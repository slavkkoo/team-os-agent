# team-os-agent — командный AI-агент («AI chief of staff») в Telegram

Telegram-бот, который отвечает команде вместо руководителя продукта: «есть ли у нас
фича X», «как считается Y», «что с задачей Z». Отвечает из базы знаний команды,
кода и трекера задач — и всегда указывает источник. Плюс сам ведёт регулярную
работу (duty): дневной дайджест рабочих чатов, «голос клиентов» за неделю,
еженедельную синхронизацию базы знаний с кодом, напоминание о решениях и
самообучение на собственных тяжёлых ответах.

Шаблон извлечён из работающей прод-системы автора и обезличен: предметка заменена на
выдуманный SaaS «Acme» (онлайн-запись), имена агента, команды и продукта задаются в `.env`.
Методика Team OS — по мотивам Team OS Toolkit Байрама Аннакова.

Это одна из трёх частей Team OS:

- **team-os-agent** (этот репо) — агент команды: бот + duty.
- [team-os-knowledge](https://github.com/slavkkoo/team-os-knowledge) — репо знаний,
  которое агент читает (клонируется в `knowledge/`).
- [personal-agent](https://github.com/slavkkoo/personal-agent) — личный ассистент
  владельца (почта, календарь, личка), отдельная граница доверия.

Установка с нуля — [INSTALL.md](INSTALL.md).

## Из чего сделан

Python 3.11+ (только stdlib; Telethon — в venv, только для чтения Telegram-папок) +
headless Claude Code (`claude -p`) на подписке (`claude setup-token`, API-ключ не нужен) +
systemd на VPS. Без фреймворков, Docker и векторной базы: агент сам читает markdown и
код встроенными Read/Grep.

## Как этим пользоваться (сценарии)

**Вопрос в личке.** Тиммейт пишет боту: «Как работает отмена брони за час до записи?»
Бот отвечает «Принял, проверяю источники», через минуту — короткий ответ по сути,
сверенный с кодом, и строка «Источник: product/booking.md». Тот, кто не в `TEAM_IDS`,
получает публичный режим: только база знаний, без кода и трекера.

**Вопрос в группе.** В рабочем чате кто-то спрашивает, что знает база, — тегните
`@<бот>` или ответьте реплаем на его сообщение. Бот ответит в треде. Реплай на чужое
сообщение с тегом бота — «ответь вот на это».

**Скриншот или файл.** Команда может прислать скрин ошибки, PDF или лог (до 10 МБ) —
бот откроет вложение и разберёт, что на нём.

**Поправка.** Бот ошибся — ответьте на его сообщение «ошибаешься, …» или «на самом
деле …». Поправка ложится в staged. Раз в неделю владелец получает список и в личке
боту пишет `promote <slug>` или `reject <slug>` (`learnings` — список). Принятые
поправки сразу подмешиваются в каждый ответ поверх базы знаний.

**Утро.** В командный канал приходит дайджест рабочих Telegram-папок за сутки
(🟡 главное, ⚪ остальное), а владельцу в личку — отдельно блок 🔴 «Требуется от
владельца». Дайджесты сохраняются — это память «что я пропустил» и вход brain-sync.

**Понедельник.** Агент обновляет клоны кода; проверяет, какие факты базы могли
устареть (код по их путям менялся после записи); делает brain-sync и присылает
ссылку на PR в базу знаний; за час до вашей встречи присылает список решений,
ждущих вердикта, и staged-поправки.

**Среда.** Learn-from-questions: агент берёт свои ответы недели, на которые ушло
много шагов, и предлагает переиспользуемые факты — веткой на ревью. Если база
говорит одно, а код другое, это приходит владельцу отдельным списком противоречий
и в базу не попадает.

**Пятница.** «Голос клиентов»: повторяющиеся боли, запросы и риски ухода из
клиентских чатов за неделю — с дедупом и честной оценкой силы выборки.

**Ежедневно.** Вторая модель ревьюит ветки конвейеров (brain-sync, learn-questions)
и пишет владельцу «можно мёржить» или что не так.

**Из терминала.** `bin/ask.sh "вопрос"` — тот же промпт и те же запреты, что у бота,
без Telegram (`PUBLIC=1` — проверить публичный режим).

## Архитектура

```
 Telegram (личка / группы / канал)
        │ long-poll getUpdates
        ▼
 bin/team_agent_bot.py   ← единственный постоянный процесс (stdlib), team-agent.service
   │  промпт: prompts/system.md + team-tools.md + tools-*.md + approved-поправки
   │  на каждый вопрос — короткоживущий subprocess, таймаут 300/600 с:
   ▼
 claude -p --model $MODEL_ANSWER --disallowedTools …
   ├─ команда:   CLAUDE_CONFIG_DIR=.claude-config,        cwd=AGENT_HOME
   │    READ  knowledge/   — клон репо знаний (git pull раз в 30 мин)
   │    READ  code/<репо>  — клоны кода (по ключевым словам вопроса)
   │    EXEC  bin/gl       — GitLab REST, только чтение
   │    EXEC  bin/code-git — git log/show/blame по code/, без опасных флагов
   │    EXEC  connectors/* — логи/метрики, API продукта, MCP… (только включённые, см. «Коннекторы»)
   └─ публичный: CLAUDE_CONFIG_DIR=.claude-config-public, cwd=knowledge/
        READ  knowledge/   — и больше ничего, Bash запрещён целиком

 systemd-таймеры (duty) ── bin/run_*.sh ── bin/lib/duty.sh (таймауты, алерты, ветки)
   │  read_chat.py (Telethon, user-сессия) → дампы папок → claude -p --model $MODEL_DUTY
   └─ знания → рабочая копия → ветка → push → ссылка на PR владельцу (не в main)

 хост (root): notify-failure@ (OnFailure любого юнита) · teamos-watchdog (10 мин)
              teamos-backup (ежедневно) · teamos-notify (алерт владельцу через бота)
```

## Duty

Время — локальное в поясе `TZ` из `.env` (install.sh рендерит его в `OnCalendar`).
Поставьте свой пояс и подвиньте время под свой ритм в `deploy/systemd/*.timer.in`.

| Юнит | Когда | Что делает | Куда |
|---|---|---|---|
| `team-agent.service` | всегда | Q&A в личке и группах, liveness дайджеста | — |
| `team-agent-digest` | ежедневно 09:30 | дайджест папок `DIGEST_FOLDERS` за 24 ч (≤2000 симв.) | 🔴 владельцу, остальное в `DIGEST_CHAT_ID` |
| `team-agent-codesync` | пн 07:00 | pull/clone репо из `config/code-repos.txt` | ошибки и обновления владельцу |
| `team-agent-stalefacts` | пн 08:00 | факты с «срез ДАТА», код по которым менялся | владельцу |
| `team-agent-brainsync` | пн 10:00 | brain/now.md, глоссарий, модель, decision-mining → ветка `brain-sync/…` | ссылка на PR владельцу |
| `team-agent-decisions` | пн 11:00 | pending-решения из `decisions.md` + staged-поправки (без LLM) | владельцу |
| `team-agent-questionlearn` | ср 14:00 | факты из тяжёлых ответов → ветка `learn-questions/…`; противоречия отдельно | владельцу |
| `team-agent-voc` | пт 11:00 | «голос клиентов» из `VOC_FOLDERS` за 7 дней (≤3000 симв.) | `DIGEST_CHAT_ID` |
| `team-agent-mergereview` | ежедневно 16:00 | ревью веток конвейеров моделью `MODEL_REVIEW`; авто-мёрж выключен | владельцу |
| `teamos-watchdog` (root) | каждые 10 мин | бот, диск, свежесть бэкапа, ваши TCP/HTTP-проверки | алерт на смену состояния |
| `teamos-backup` (root) | ежедневно 04:00 | память, секреты, сессия, юниты → `/var/backups/teamos` | — |
| `notify-failure@` (root) | OnFailure | упавший юнит → алерт с хвостом журнала | владельцу |

Duty без настроенных входов просто выходят (нет `DIGEST_FOLDERS` — нет дайджеста),
поэтому включать можно по одной.

## Безопасность и границы

Это главная ценность шаблона: агент читает чужие тексты (сообщения, вложения, задачи,
дампы чатов), а значит, любой из них может оказаться prompt-injection.

- **Два режима и физическая изоляция.** Команда (`TEAM_IDS`) и все остальные запускаются
  с разными `CLAUDE_CONFIG_DIR` (`.claude-config` / `.claude-config-public`) и разной рабочей
  папкой. Публичный режим стартует с `cwd=knowledge/`: Claude Code разрешает читать cwd, и
  при `cwd=AGENT_HOME` собеседник мог бы прочитать логи и дампы. Bash в публичном режиме
  запрещён целиком; вложения от не-команды не скачиваются.
- **Запреты на ответы в чате** (`--disallowedTools`): нет Edit/Write, нет `python3`/`bash`/`sh`/
  `git -C`, нет чтения чужих диалогов (`memory/dm`), поправок, дампов чатов (`*_run`),
  Telegram-сессии (`tg/`). Duty получают нужные им права точечно через `--allowedTools`.
- **settings.json deny**: `.env*`, токен Claude, `.claude-config*`, `~/.ssh`, `/root`, `curl`, `wget`,
  `env`, `printenv`, `git push`, `WebFetch`, `WebSearch`; запись в `knowledge/` и `code/`.
- **Секреты не в окружении модели**: бот вычищает `TG_BOT_TOKEN`, `TG_API_*`, `GITLAB_TOKEN` и
  переменные коннекторов (`LOGS_ES_*`, `PRODUCT_API_*`, `HELPDESK_*`, `GITHUB_*` …) из env
  дочернего `claude`; `bin/gl` и обёртки коннекторов сами читают свои токены. Токены не попадают в `ps`:
  curl получает URL с токеном через конфиг на stdin, git — через `GIT_ASKPASS`.
- **Инструменты только на чтение.** `bin/gl` — только GET; `bin/code-git` — белый список
  подкоманд, запрет `--output`, `--ext-diff`, `-c core.pager` и т.п. Единственное исключение —
  коннектор product-api с отдельно включаемой записью на тестовом аккаунте: только из лички
  команды, с предохранителями в обёртке, ledger и автоочисткой.
- **Коннекторы выключены по умолчанию** и подключаются только в полном режиме команды; MCP —
  по белому списку инструментов, пишущие инструменты отклоняются без явного флага.
- **Знания — только через ревью.** Конвейеры коммитят лишь свою зону путей в отдельную ветку
  и присылают ссылку на PR. `mergereview` по умолчанию не мёржит (`MERGEREVIEW_AUTOMERGE=0`);
  включите защиту ветки `main` в репо знаний.
- **Потолки.** `GLOBAL_DAILY_LIMIT` на всех, `PUBLIC_USER_DAILY_LIMIT` на каждого не из
  команды, `PUBLIC_DM=0` — закрыть личку для чужих, `ALLOWED_GROUP_IDS` — только ваши группы.
- **Таймауты везде.** Ответ — 300/600 с; каждый `claude -p` в duty — через `duty_claude` с
  обязательным таймаутом и явной моделью; юниты — `TimeoutStartSec`.
- **Тишина ≠ успех.** Сбой ответа → алерт владельцу (не чаще раза в 15 мин на тип). Duty
  различает «упёрлись в лимит подписки», «таймаут», «упал», «пустой ответ» и сообщает о каждом.
  Упавший юнит → `notify-failure@`. Дайджест не обновлялся 26 ч → liveness-алерт из бота.
- **Персональные данные.** Буферы личек обрезаются до последних 500 записей, вложения живут
  неделю, дампы чатов лежат только в `*_run/`. Промпты duty запрещают переносить в базу
  коммерческие условия и персональные данные.

Чего агент НЕ делает: не пишет в репо знаний и код напрямую, не трогает прод, не отправляет
сообщения от вашего имени (Telethon-сессия только читает), не принимает решения за людей —
pending-решения и противоречия всегда уходят человеку.

## Настройка и кастомизация

- Все переменные — в [.env.example](.env.example) с комментариями.
- Код — `config/code-repos.txt` (`имя url ветка [ключевые,слова]`): репо с ключевыми словами
  подключается к вопросу, только если слово есть в вопросе (большой фронтенд не мешает
  вопросам про бэкенд).
- Поведение модели — только в `prompts/*.md`. Плейсхолдеры: `{{AGENT_NAME}}`, `{{TEAM_NAME}}`,
  `{{PRODUCT_NAME}}`, `{{OWNER_REF}}`, `{{TZ}}`, `{{TODAY}}`, `{{REPO}}` и служебные (`{{QUESTION}}`,
  `{{CONTEXT}}` …). Подстановка — за один проход: текст `{{…}}` в вопросе пользователя не
  разворачивается. Шаблон duty с незаполненным плейсхолдером не уйдёт в модель — duty упадёт
  с алертом. Бот перечитывает изменённый промпт без рестарта.
- Меняйте промпты в своём форке и выкатывайте `deploy.sh` — не правьте файлы на сервере.
- Ожидаемая структура базы знаний (всё необязательно): `CLAUDE.md` — точка входа для
  навигации, `product/`, `brain/now.md`, `brain/product/{glossary,object-model}.md`,
  `brain/skills/update-knowledge/SKILL.md`, `decisions.md`. Готовый шаблон —
  [team-os-knowledge](https://github.com/slavkkoo/team-os-knowledge).

ни на байт. Подробно (права, риски, адаптация) — [connectors/README.md](connectors/README.md).

## Что можно добавить

Всё это можно добавить — в шаблоне этого нет, вот на что обратить внимание.

- **Маршрутизация моделей** по типу вопроса. Внимание: дешёвая модель теряет нить на
  многошаговом поиске по идентификатору; экономия на «простых» вопросах легко съедается
  повторными вопросами.
- **Предзагрузка данных** по идентификатору из вопроса до запуска модели (например, трейс через
  logs-metrics) — минус 2-4 шага на каждый ответ. Внимание: только для команды, молча без
  предзагрузки при ошибке.
- **Встречи и транскрипция** (meeting-бот → решения → `decisions.md`). Внимание: согласие
  участников на запись; в базу — решения, не стенограмма.
- **Notion / вики как источник** — проще всего через коннектор mcp с read-only токеном.
  Внимание: в базе — указатели и «как обещано», живое состояние остаётся в системе записи;
  расхождения с кодом фиксировать.
- **Ambient-контекст в группах** (последние N сообщений чата в промпт). Внимание: нужен
  privacy mode OFF — бот видит всё; буфер ротировать и ограничить; тянуть фон только для
  явных продолжений, иначе ответы смешивают темы.
- **Связка с личным агентом** (триаж бэклога, «что ждёт от меня команда») —
  см. [personal-agent](https://github.com/slavkkoo/personal-agent). Внимание: это другая граница
  доверия — отдельный пользователь ОС, отдельные секреты.

## Грабли (уроки прода)

- **409 Conflict при двух экземплярах бота.** Telegram отдаёт `getUpdates` только одному
  процессу на токен. Переезд — «поднять новый → проверить → погасить старый» быстро, или
  временный второй токен. Тот же 409 вы увидите, если дёргать `getUpdates` руками при живом боте.
- **VPN full-tunnel выбивает SSH.** Если сервер ходит во внутренний GitLab через VPN, клиент
  с `redirect-gateway` уводит весь трафик в туннель — и вы теряете SSH. Только split-tunnel
  (`pull-filter ignore "redirect-gateway"` + маршруты внутренних сетей). Один сертификат VPN
  на двух машинах — они выбивают друг друга.
- **Дрейф кода на сервере от git.** «Быстро поправлю на сервере» — и через месяц прод
  работает на коде, которого нет в репо. Поэтому `deploy.sh` делает `reset --hard` на
  `origin/main` и откатывается при сбое: деплой только из git.
- **Тишина ≠ успех.** Duty без таймаута висит вечно; duty без проверки кода возврата
  отправляет обрезанный ответ в канал как нормальный; упор в лимит подписки выглядит как
  «пустой день». Отсюда `duty_claude`, OnFailure, watchdog и liveness.
- **Бэкапов не было** — пока не понадобились. Память бота (поправки, offset, контексты),
  Telegram-сессия и секреты невосстановимы из git. Бэкап на том же диске не спасает от
  потери сервера — забирайте копию на другую машину.
- **Промпт f-строкой в коде нельзя ревьюить.** Десятки килобайт правил в одной строке
  Python не диффаются и ломаются при каждой правке. Поэтому поведение — в `prompts/*.md`,
  а `ask.sh` берёт промпт из бота, а не держит свою копию.
- **Конвейеры не должны пушить в main без ревью.** Ночные конвейеры, коммитящие прямо в
  канон, быстро наполняют его фактами, которые уже разошлись с кодом. Только ветка + PR,
  `last_reviewed` — дата ревью человеком, конвейеры ставят `bot_updated`.
- **Клиентам ушли отчёты из «н/д».** Источник метрик лежал несколько дней, а ежедневный отчёт
  исправно уходил клиентам — из одних «н/д». Отсюда правило client-reports: нет данных — не
  отправлять, владельцу алерт с черновиком.
- **Судья eval завышает галлюцинации.** LLM-судья помечает галлюцинацией верный ответ,
  если не нашёл подтверждения сам. Считайте честно: выборку вердиктов ревьюит человек.
- **Мёрж «прошёл», а влито ничего.** Мёрж упал на конфликте, скрипт запушил неизменённый
  main и отчитался «смёржено». Проверяйте результат мёржа, а не код возврата push.
- **`git add` по несуществующему пути** не добавляет вообще ничего — конвейер молча теряет
  все правки. Добавлять пути по одному.
